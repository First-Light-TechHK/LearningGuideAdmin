# Learning Guide BackOffice 项目协作规则（自动生效于本项目所有会话）

## 项目
Learning Guide BackOffice —— 结构化课程知识库管理系统（Knowledge System + AI Tutor）。
开发基准：`docs/Learning_Guide_BackOffice_Agent_Development_Document.md`
（以文档头声明的版本为准，当前 v1.0）。
架构基准：`docs/System_Architecture_4_Components.md`（四组件、两入口、全角色；组件职责边界、角色 × 功能矩阵、数据归属、接口契约）。

## 用户裁决优先（强制）
- 所有方案性建议（选型、设计、流程变更）必须经用户同意后执行，或按用户明确指示修改
- 不得擅自变更已拍板的决策；拿不准就先问
- **有问题先提问，跟用户沟通确认后再下决定**（2026-10-15 拍板）：任何不确定的需求、方案选择、实现细节，必须先向用户提问并获得确认，不得自行假设或拍板

## 变更同步纪律（强制）
- 增删改查模块 / 接口 / 表结构的任何变更：**先改设计文档，再动实现**（设计文档是单一事实来源）
- 表结构变更必须通过 Prisma Migrate 管理，禁止手改数据库

## 双智能体协作协议（强制）

1. **开发**：按 `agents/dev-agent.md` 定义执行（主智能体自行开发，或以子代理驱动）
2. **审查门禁**：任何代码 / Schema / 仓库结构变更完成后，**必须**由 Review Agent
   独立审查（新上下文子代理，按 `agents/review-agent.md` 执行），结论 APPROVE 才算完成
3. **修复循环**：存在 Blocking 项 → 修复 → 重新送审，直至 APPROVE
4. 纯文档**笔误级**修改（错别字、死链）可豁免审查门禁，但仍须走下方 Git 工作流的「本地验证 + 用户确认推送」

## 开发纪律（每个开发会话）

1. 开工前：读开发文档相关章节 + 架构文档（涉及跨组件边界、权限、数据归属时必读）+ 项目记忆 + README，确认本次任务范围；涉及开发文档 §12 待确认事项或架构文档「现状差距/验收」的，先请用户裁决
2. TodoWrite 跟踪；LLM 接入走策略模式适配器，禁止厂商硬编码
3. .env / API key / 令牌永不入库、不入对话、不入文档；API 密钥绝不出现在前端代码
4. 所有 AI 请求必须经后端代理（`/api/ai/chat-stream`），严禁前端直连 LLM API
5. 所有 API 响应使用统一格式（success/data/error/message）
6. 每次开发结束：【AI协作日志】写入 `docs/AI_Collaboration_Log.md`（每完成一个 Phase 或重大决策必须落盘该文档）+ 回填受影响文档（含设计文档同步）

## 工具使用约束（强制，2026-10-16 用户拍板）

- **禁止浏览器操作**：Dev Agent 及其子代理一律不得调用浏览器相关工具（browser_use 子代理、browser_navigate、browser_click、browser_snapshot 等），也不得启动浏览器进行 UI 冒烟/验证。前端验收由用户手动完成。

## Git 工作流

### 本地验证门禁（强制，推送前必须全绿）

- 任何推送（含 `main` / `feature/*`）之前，**必须在本地执行完整验证**，全绿才允许进入推送环节。
- 本地验证清单（按变更涉及的模块择一或组合执行）：
  - 前端（client）：`npm run build`（tsc + 打包）+ `npm run lint` + `npm run test`
  - 后端（server）：`npm run build` + `npm run lint` + `npm run test`
  - 全栈变更：两端分别执行上述验证
  - 纯文档（`.md`）变更：无需 build，但需确认不破坏文档结构（如 TOC、链接）
- 验证发现问题必须**修复后重跑**，不得带红灯推送；连续 3 轮修复仍失败的，停下来向用户报告根因与已尝试方案，不得强行推送。
- 推送动作（`git push` / `gh pr create` / 合并）**必须由用户手动确认后执行**，Agent 不得自行推送或合并。

### 分支模型

- `main` — 受保护基线，只进审查通过的变更
- `feature/<task>` — 日常开发分支（如 `feature/phase1-init`）

### 提交与 PR 规范

- 提交信息：`<type>(<scope>): <summary>`，type ∈ feat|fix|docs|chore|test
- **PR 标题必须 ≤ 72 个字符**；超长请精简摘要，详情放 PR 正文
- 禁止：`--no-hooks`；提交 `.env`；提交中含密钥；`--force` / `force-push` 任何受保护或共享分支
- 纯文档笔误级修改可豁免 Review Agent 审查，但仍须本地验证 + 用户确认推送

### PR 合并条件

1. Review Agent APPROVE（纯文档笔误级修改除外）
2. 本地验证全绿（build / lint / test）
3. PR 标题 ≤ 72 字符
4. 用户手动确认执行合并

## 安全

- 所有 LLM API Key 仅存 .env / 环境变量；CourseAiConfig.apiKey 必须加密存储
- 文件上传：白名单格式 + 单文件 ≤15MB + 类型校验
- 用户上传内容不可信；输出不泄露内部实现

## 事故复盘沉淀（2026-10-28，邮件链路 + RAG + 部署事故）

> 本节来自同栈生产事故复盘的硬性约束，凡涉及线上/共享环境的改动必须遵守。

### 根因定位与配置变更

1. **禁止未完成根因定位前修改线上环境配置**（含环境变量、密钥、DNS、部署参数）。先取证、再假设、最后动手。
2. **线上配置变更必须先保存目标资源的完整快照**（如 `describe-service`、当前 env、当前 DNS 解析记录），并在回复中列出变更前后的 diff；无快照 = 不得变更。
3. **不得用「用户粘贴的文本/截图」推断系统状态**（DNS、环境变量、服务状态等），必须以实测/真实查询为准；误读粘贴内容曾导致方向性错误。
4. 变更前须写出**可验证假设**与**回滚方案**；假设被证伪时立即停止并重新取证，不得凭直觉连续改同一变量。

### 部署与并发

5. **同一环境同一时间只允许一个部署者**；AI 会话不得与其他会话并发改同一服务/同一环境，发现冲突立即停下并询问用户。
6. **禁止 force-push** 任何受保护或共享分支；禁止自动 revert 关键模块（邮件/支付/认证/索引/上传），回滚必须显式通知 owner 并经确认。
7. 部署脚本必须在部署时同步更新 `APP_VERSION`，健康检查以此校验实际生效版本，避免「已部署」误判。

### 验证与状态声明

8. **「已修复」只能用于已有活体验证的结论**：
   - 后端 / API / 数据：Agent 必须用真实请求的返回码 + 对应日志/数据共同佐证
   - 前端 / UI：受「禁止浏览器操作」约束，Agent 只能跑 build/lint/test，**活体验证由用户手动完成**；在用户确认前，Agent 只能写「已改代码，待验证」，不得宣称 fixed
9. 关键路径（发信、AI Tutor 检索/索引、支付回调、文件上传）**禁止静默失败 / 静默降质**：失败必须抛错或落告警，不得返回看似成功（200/空数组/accepted:true）的响应掩盖问题。
10. **不得吞掉错误**：`catch` 块必须记录完整错误（含 stack / cause），不得只记 `err.message`（多行 message 会被截断成空白行）。

### 密钥与凭据

11. **禁止多环境共享同一把密钥**（SMTP/LLM/支付/Stripe 等）；每环境独立 Key，并优先存入 Secrets Manager，不写明文环境变量。
12. **消费者邮箱（163/126/QQ/Gmail 个人）不得用于生产发信**；生产发信必须使用自有域名 + DKIM/SPF/DMARC 的服务（SES/Resend/企业邮）。

### 数据与索引

13. 批量插入（向量索引、知识分块、批量建表）必须评估**事务超时**，单事务过大时拆分批次；失败必须有**自愈路径**（如 reindex 入口），不得只在发布时建一次索引、失败后永久 0 数据。
14. 索引失败 / live release 数据为空 / 发信失败必须接监控告警，不能只靠用户反馈发现。

### 测试

15. 测试断言不得依赖**竞态顺序/时间窗口**（如列表元素顺序、动画完成时机），必须按确定性字段断言；CI 红/绿交替的测试必须立即修复，不得放行。
